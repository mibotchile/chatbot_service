# Design: PrestamYpe — Correct Balance, Enrich "Tu Crédito", Lighter Comprobante

## Technical Approach

Three coordinated changes on the live Doris path (`data_source: doris`, fail-closed, no fixture fallback): (1) redesign `_build_sql` so balance/cuota/vencimiento/días-mora come from the FIRST UNPAID installment and assignment fields come from the LATEST batch; (2) surface `inversionista` + `cuenta_bancaria` in the debt card and templates; (3) make `validar_comprobante` server-validated and lighter. Doris facts are confirmed live (P04197). Implements spec capabilities `cobranza-balance`, `cobranza-credit-display`, `cobranza-comprobante`.

## Architecture Decisions

### Decision: `_build_sql` strategy — config-driven `pagos_selection` (Option A)

| Option | Tradeoff | Decision |
|---|---|---|
| A. Add a `pagos_selection` block + per-column `from_selected_row` to `doris_schema` (window function generated by builder) | Slightly more builder logic; reusable for any cobranza tenant with installment schedules | **CHOSEN** |
| B. Prestamype-specific SQL path branched by tenant_id | One-off hack; abandons the tenant-agnostic contract the module advertises | Rejected |

**Rationale**: The module's whole premise is tenant-agnostic SQL from config. A flat `agg:MAX` can express neither "first-unpaid row" nor "latest batch". Other cobranza tenants (RECSA-style schedules) will need the same first-unpaid semantics, so generalizing earns its complexity. Option B would betray the existing design and rot.

**Mechanism**: `doris_schema` gains two blocks. `batch_selection` (assignment latest-batch) and `pagos_selection` (first-unpaid). The builder wraps `batch_pagos_v2_bronze` in a `ROW_NUMBER()` subquery and the assignment table likewise, then joins both filtered to `rn = 1`. Columns flagged `from_selected_row` read from the selected pagos row; everything else from the selected assignment row. `agg` support stays for backward compat with other tenants but Prestamype drops it.

Target SQL shape:

```sql
WITH pagos_sel AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY codigo_contrato
    ORDER BY (fecha_de_pago_del_cliente IS NULL) DESC,  -- unpaid first
             fecha_de_pago_esperada_original ASC
  ) AS rn
  FROM <db>.batch_pagos_v2_bronze
),
asig_sel AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY id_credito
    ORDER BY creado_el DESC, archivo DESC
  ) AS rn
  FROM <db>.batch_asignacion_review_bronze
)
SELECT a.<assignment cols>, p.<installment cols>
FROM asig_sel a
JOIN pagos_sel p ON p.codigo_contrato = a.id_credito AND p.rn = 1
WHERE a.dni_ruc = %s AND a.rn = 1
```

Field provenance:
- **First-unpaid pagos row**: `balance`/`saldo_por_cancelar`←`saldo_por_cancelar`; `cuota_esperada`/`next_installment_amount`←`COALESCE(cuota_esperada_actualizada, cuota_esperada_mensual)`; `next_due_date`←`fecha_de_pago_esperada_original`; `days_overdue`←`dias_de_atraso_de_pago` (or derived).
- **Latest assignment row**: `inversionista`, `cci`←`codigo_de_cuenta_cci`, `cuenta_bancaria`←`numero_de_cuenta`, `banco`, `borrower_name`, `dni`, `email`, `phone`.

The unpaid-first ordering makes the fully-paid case fall through to the last installment (saldo 0) — satisfies spec's "fully settled" scenario.

### Decision: cuota fallback as SQL `COALESCE`, not Python

**Choice**: `COALESCE(cuota_esperada_actualizada, cuota_esperada_mensual)` in the generated SELECT (declared via a `coalesce` list in the column spec).
**Alternatives**: Python-side fallback in `_row_to_profile`. **Rationale**: Keep the row→profile mapper thin; the data rule belongs in the query so other consumers get it too.

### Decision: Comprobante validated server-side; inversionista mismatch = WARN

**Choice**: `validar_comprobante` resolves CCI + inversionista from the verified profile (Doris), classifies by monto, and treats an inversionista mismatch as a non-blocking warning while still storing EN REVISIÓN. User no longer types CCI/nro_operacion.
**Alternatives**: Reject on mismatch. **Rationale**: Spec mandates human conciliation; the bot must never hard-reject a real payment. Mismatch is a flag for the reconciler, not a gate.

## Data Flow

```
DNI ─→ resolve_dni ─→ _build_sql(first-unpaid + latest-batch) ─→ Doris
                                                                   │
profile{balance,cuota,inversionista,cuenta_bancaria,cci} ←────────┘
   │                              │
   ├─→ consultar_deuda ─→ debt card (widget) + responses.json templates
   └─→ validar_comprobante(monto, inversionista?) ─→ classify vs cuota/saldo
                                                   └─→ audit JSON (EN REVISIÓN, +inversionista)
```

## Interfaces / Contracts

`validate_comprobante(profile, monto, *, inversionista=None, id_credito=None)` → `{cuenta_valida, credito, tipo, cuota_esperada, saldo_por_cancelar, inversionista, inversionista_match: bool|None, dedup_ok, estado:"en_revision", mensaje}`. CCI sourced from `profile["cci"]`, never user input.

## Testing Strategy

| Layer | What | Approach |
|---|---|---|
| Unit | first-unpaid selection, latest-batch filter, cuota COALESCE fallback | Mock cursor returning crafted rows; assert generated SQL contains ROW_NUMBER + partitions and that `_row_to_profile` yields 81,510.15 / 7,031.91 / 2026-03-02 for a P04197-like fixture |
| Unit | comprobante classify + mismatch warn + anti-dup | Call `validate_comprobante` with profile fixture; monto≈cuota→pago, ≈saldo→cancelación, wrong inversionista→`inversionista_match=False` but `estado=en_revision`; duplicate→`dedup_ok=False` |
| Unit | debt card / templates render inversionista+cuenta, omit capital, NULL graceful | Render `consultar_deuda` dict; assert keys present/absent |
| Integration (live) | end-to-end SQL against Doris P04197 | Optional, gated; not in CI (cobranza_ro, no fixtures) — run manually pre-apply |

Strict-TDD: write the SQL-shape and classification tests first (mock-based, no live Doris). Live Doris is verification-only.

## Migration / Rollout

No schema migration. `data_source` stays `doris`. Rollback = `git revert` (config + SQL builder + templates are scoped); reverting restores the known-wrong `agg:MAX` prod behavior.
